# Структура проверки: кто, что и что пишет

Проверка идёт восемью параллельными агентами плюс основной сессией. Разделение сделано так,
чтобы области чтения почти не пересекались, а файлы, которые разрешено менять, не пересекались
вообще: только два агента могут писать, и пишут они в разные каталоги.

## Карта агентов

| # | агент | зона | читает | пишет |
|---|---|---|---|---|
| R1 | `reviewer` | модели, кросс-валидация, метрики | `src/spp/models/*`, `features/labels.py`, `features/calendar.py` | — |
| R2 | `reviewer` | бэктест, портфель, издержки | `src/spp/backtest/*`, `reports/test_2023_predictions.parquet` (только нужные колонки) | — |
| R3 | `reviewer` | сентимент-слой | `src/spp/sentiment/*`, `reports/calibration/*`, `tests/test_openjev_batching.py` | — |
| R4 | `reviewer` | CLI, ops, конфиг, упаковка | `src/spp/cli.py`, `config.py`, `ops/*`, `pyproject.toml`, `.gitignore` | — |
| G1 | `quant-guard` | статистика и все публичные числа | `results/*`, `reports/runs/*`, `README*.md`, `docs/*` | — |
| D1 | `quant-docs` | документация | README, docs, `git ls-files` | `docs/*.md`, `README.md`, `README.ru.md` |
| I1 | `implementer` | исправление подтверждённых дефектов | код + тесты | `features/sentiment_daily.py`, `data/news_live.py`, `data/prices.py`, `tests/*`, `docs/known-issues.md` |
| M1 | `researcher` | методология против литературы | `models/cv.py`, `models/metrics.py`, `backtest/*` | — |

## Почему именно такое деление

* **R1–R4** — четыре независимых «разреза» кода одной природы (чтение, поиск дефектов), поэтому их
  можно вести одновременно без конфликтов и без дублирования: граница проходит по каталогам.
* **G1** не читает код, а сверяет артефакты с текстом. Это единственный агент, который может
  поймать «число в README не равно числу в `results/`».
* **D1** — единственный, кому разрешено править публичный текст, и ему прямо запрещено трогать
  числа аблаций/holdout: они генерируются `ops/make_ablation_report.py`, ручная правка создаёт
  расхождение с артефактами.
* **I1** правит только те дефекты, которые **не меняют численный результат** залоченного holdout
  2023. Всё, что меняет признаки (моментум `ret_k`, `n_news_z`, EWMA-возраст, атрибуция тикера),
  уходит в `docs/known-issues.md` как решение владельца, а не как молчаливая правка.
* **M1** не ищет баги — он отвечает, какие решения в проекте расходятся с принятой практикой
  (purged CV по López de Prado, HAC для IC, поправка на множественные сравнения, Deflated Sharpe).

## Порядок и гейты

```
          ┌─ R1 ─┐
          ├─ R2 ─┤
          ├─ R3 ─┤        ┌── триаж находок ──► I1 (только безопасные) ──► тесты+ruff
          ├─ R4 ─┘        │
          ├─ G1 ──────────┤
          ├─ D1 ──────────┘   (D1 правит только текст, не числа)
          └─ M1 ──► рекомендации, требуют решения владельца

Параллельно (основная сессия):
  open-jev scoring → ops/ablate.py --only a3 a8 → train a3 / a8 → ops/ensemble_a7.py
  → ops/make_ablation_report.py → commit + push
```

Гейты:

1. `ruff check src tests ops` → чисто; `pytest -q` → зелёный. Без этого правки I1 не принимаются.
2. A8 нельзя собирать до исправления `_flag_stats`: иначе `company_specific_share` и
   `novelty_mean` останутся NaN и A8 будет измерять отсутствие признака, а не его эффект.
3. Числа в README обновляет только `ops/make_ablation_report.py`; D1 правит лишь пути, флаги,
   названия файлов и счётчики.

## Классификация находок

* **P0** — искажает опубликованный результат (утечка, неверная метрика, неверное число в README).
  Требует перепрогона затронутой части и правки текста.
* **P1** — ломает будущий прогон или живой пайплайн (как `_flag_stats`, из-за которого A8 был бы пуст).
* **P2** — не влияет на текущие выводы, но искажает диагностику или отчётность (воронка фидов,
  неидемпотентный отчёт аномалий).

## Что считается результатом проверки

1. Таблица находок с `файл:строка`, сценарием отказа и способом проверки — по каждому агенту.
2. `docs/audit-docs.md` — расхождения документации с кодом.
3. `docs/known-issues.md` — дефекты, которые сознательно не исправлены, с оценкой влияния.
4. Исправления I1 с тестами, покрывающими каждый дефект.
5. Отчёт M1 с рекомендациями по методологии и список решений, которые нужно принять до
   внутридневного эксперимента (`docs/idea-intraday-t5.md`).
